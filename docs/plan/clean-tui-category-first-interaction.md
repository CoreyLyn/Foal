# Plan: Clean TUI category-first interaction

A design note maintained during the Clean TUI grilling session. The interaction is the implemented primary Clean TUI surface (cutover complete): category-first eager preview replaces the old whole-report loading cycle while preserving Foal's shared Clean safety model.

## Goal

Make Clean immediately understandable and operable: show every cleanup category, measure categories progressively, let the user form an exact cleanup selection, keep its known total visible, then move through a separate confirmation into shared Clean execution.

## Resolved decisions

- Entering Clean starts a read-only, sequential eager preview scan of every canonical default and opt-in cleanup category. Permission-boundary catalog entries remain notices rather than scan targets. Non-executable Review suggestions and review clues are not cleanup categories, do not appear in this category-first list, and do not affect scan completion or confirmation; both remain available through their existing non-TUI preview contracts.
- Eager scanning does not select or authorize opt-in categories. Confirmed execution still fresh-resolves selected category identifiers and never consumes preview paths.
- Default categories start selected but may be cleared. Opt-in categories start unselected. The TUI must execute exactly the confirmed category selection without silently adding defaults. The exact plan accepts canonical default and opt-in identifiers only; permission-boundary identifiers, review-only evidence, aliases, group tokens, and paths cannot enter it.
- The category list is usable while scanning continues. The user may navigate and change selection for waiting, scanning, or completed categories.
- Selection changes never restart scanning. A selected category contributes bytes to the current known total only after its measurement completes; unfinished bytes are neither guessed nor counted.
- A visible row cursor and cleanup selection are separate states. Up and Down move the cursor only, Space toggles the focused category, and Enter opens the separate confirmation view; cursor movement never changes cleanup authorization.
- Enter remains unavailable until every scannable category reaches a terminal path-free outcome: complete, partial, empty, skipped, incomplete, or failed. Non-success outcomes finish the scan without inventing bytes, so diagnostics cannot leave confirmation blocked indefinitely. Until then, the header keeps `Scanning n/N · Confirmation available after scan completes` visible even when every currently selected category is already terminal.
- While any selected category is unfinished, the primary summary is `Selected: N categories · X measured · M pending`, where `N` includes every selected category, `X` sums safely completed preview bytes for selected default and opt-in categories in complete or partial state, and `M` counts selected waiting or scanning categories. The three values update immediately when selection or scan state changes; unfinished bytes are never represented as zero. After every selected category is terminal, the summary collapses to `Selected: N categories · X`. Empty, skipped, incomplete, and failed categories contribute zero and are automatically removed from selection, and the confirmation view identifies the final value as a latest preview that fresh execution may change.
- Existing Potential space, Observed opportunity bytes, and Opt-in reclaimable bytes semantics remain distinct in shared models and contracts; the TUI selected total is a presentation aggregate rather than a replacement contract.
- A category may be selected provisionally while waiting or scanning. If its terminal outcome is empty, skipped, incomplete, or failed, the TUI automatically clears and disables that row for the rest of the current Clean view, removes it from the selected count and total, and shows the outcome reason.
- A partial category remains selectable when at least one sibling candidate was measured safely. Its count and bytes include only complete siblings, while the focused detail explicitly reports that other siblings were excluded and why; no safe candidate means incomplete rather than partial.
- Empty is defined by candidate count, not bytes: zero candidates is empty and disabled, while one or more safely measured zero-byte candidates remain complete and selectable (for example, `Complete · 1 item · 0 KB`). Such a category contributes zero bytes but still counts as selected, and fresh execution decides whether the candidate still exists.
- Protection suppression remains distinguishable from absence without exposing protected data. If every discovered candidate is protected, the category is path-free skipped and disabled; if unprotected candidates remain, it is partial and counts only those candidates and bytes. Focused detail may show a generic stable reason and excluded count, but never protected paths, protected bytes, or raw OS messages containing paths.
- A global safety or configuration failure before scanning opens a dedicated `Clean unavailable` page instead of marking every category failed. No category queue, selection, total, confirmation, execution, detailed-list write, or history is created; the page shows only a stable code and path-free explanation, with Enter, Escape, or `b` returning to the menu and `q` quitting. Re-entering after the external problem is fixed starts a new scan.
- Display order and sequential scan order are identical: User essentials, System, Browsers, then Developer tools, with canonical catalog order inside each group. This measures the initially selected default category early and leaves potentially slower developer-tool work until last. Permission-boundary notices remain fixed below the scan list and do not enter the queue.
- Filesystem category scans keep Foal's deterministic per-entry 100,000-descendant inspection ceiling and do not add a wall-clock timeout. The category-first TUI does not invoke external tool query probes solely to discover Review suggestions; developer-cache measurement uses the canonical category's environment/default-path resolver. Existing CLI/JSON Review suggestion probes retain their per-call two-second timeout. The TUI shows a spinner and elapsed time and remains cancelable, but a truly blocked underlying filesystem call cannot be bypassed to reach confirmation.
- The current TUI scope has no retry or rescan control. Leaving Clean and entering it again starts a new eager preview scan. Focused-category retry and full-list rescan remain deliberately deferred and are not the next planned Clean slice; a future proposal must justify reopening this interaction and preserve the shared Clean safety model. Execute still fresh-resolves confirmed category identifiers, but that mandatory safety recheck is not a user-facing preview rescan control.
- Leaving during the read-only scan needs no confirmation. Escape or `b` cancels the scan and returns to the main menu; `q` cancels it and quits the TUI. The in-memory scan results and selection are discarded without history, detailed-list writes, or cleanup actions.
- Outside active confirmed execution, Ctrl+C retains the Bubble Tea interrupt path: it cancels any preview scan and exits with interrupt status 130. Active execution is the scoped cancellation exception recorded in ADR 0014.
- The primary Clean view is category-first: compact title and progress, grouped category rows, visible cursor and checkboxes, per-row state and size, selected count and total, and concise key hints. The current filter, expand, copy-path, and duplicated full-report surfaces are removed from this view. Existing Clean preview and execution CLI/JSON reports remain unchanged; only `history --json` gains the backward-compatible optional TUI provenance described below.
- Clean uses one responsive viewport policy across preview, confirmation, execution, and result views. Titles and progress stay fixed at the top; selected totals, contextual diagnostics, and key hints stay fixed at the bottom; group headings scroll with their rows; terminal resize preserves the relevant row or offset; and there is no separate scroll mode. In preview, Up and Down move the focus and the viewport follows it, including disabled rows whose diagnostics remain reviewable. In confirmation and result views, Up and Down move only the viewport offset because rows are not selectable. During execution, the active category is the automatic follow target while Up and Down pause following to inspect other rows without changing authorization; following resumes only when a newly active category is completely outside the viewport, at which point that row is scrolled into view. If the terminal cannot render the minimum safe layout, Clean replaces the content with `Terminal too small` and resize guidance. Preview, confirmation, and result keep Escape available to return and `q` available to quit; active execution instead preserves ADR 0014, shows its current phase and Ctrl+C cancellation hint, and continues to ignore Escape, `b`, and `q`.
- Preview rows keep navigation, authorization, and scan state visually separate: `>` is the cursor, `[x]`/`[ ]` is selection, `…` is waiting, an animated spinner marks the current scanner, `✓` is complete with candidates, `–` is empty, `⊘` is a safety skip, and `!` is partial, incomplete, or failed. The header shows `Scanning n/N`; no byte-derived percentage is displayed, and only the checkbox authorizes a category.
- `a` explicitly selects every currently selectable category for this session, including waiting, scanning, complete-with-candidates, and partial rows; it excludes permission boundaries and terminal empty, skipped, incomplete, or failed rows. `x` clears every selection, including defaults. Neither action persists, bypasses full-scan completion, or skips the separate confirmation and second Enter.
- A bottom contextual panel follows the row cursor without a separate key or detail mode. It shows the focused category's completed count and bytes, optional safety note, or partial, empty, skipped, incomplete, and failed reason; for partial state it also shows the excluded sibling count and stable reason. Safety notes are optional path-free evidence supplied by shared Clean within the existing impact-notice vocabulary; the TUI does not infer them from paths or invent a note for every category. Rows stay compact, disabled rows remain focusable, Space on a disabled row performs no action and leaves its reason visible, full candidate paths remain absent, and Enter remains reserved for confirmation.
- Confirmation requires a non-empty selection as well as terminal outcomes for all scannable categories. If selectable categories exist but the user clears them all, Clean shows `Select at least one category to continue.` If every scannable category terminates as empty, it shows `Nothing to clean.` If no category is selectable and at least one terminates as skipped, incomplete, or failed, it instead shows `No selectable cleanup found. Some categories were skipped or could not be measured.` Row state and the focused diagnostic provide the path-free reason. None of these states calls shared execution or creates an empty history session.
- Enter from the completed category view opens a separate confirmation page without executing. That page lists the exact selected categories, `Selected: N categories · X`, the fresh-rescan caveat, and the Recycle Bin-only action; a second Enter starts shared execution, while Escape or `b` returns with the in-memory scan results and selection intact. There is no countdown, typed phrase, or direct one-key execution from browsing.
- Execution freezes the confirmed selection and reuses the category-list language for selected categories only. The header shows a spinner and the shared phase (`Fresh scanning`, `Recycle Bin safety check`, or `Moving to Recycle Bin`); in-progress rows use `rechecking`, `ready`, and `cleaning`, then end as path-free `empty`, `cleaned`, `partial`, `skipped`, `failed`, or `canceled`. `partial` requires at least one success plus any excluded, skipped, failed, or canceled item; zero-success outcomes distinguish empty fresh resolution, all-safety skips, operational failure, and cancellation. The footer counts only terminal categories as processed and only actual successful Recycle Bin moves as affected bytes, without a byte-derived percentage. Final item-level Result and history remain authoritative.
- During execution, only Ctrl+C requests cooperative cancellation; Escape, `b`, and `q` do nothing, and repeated Ctrl+C does not force exit. The view changes to `Cancellation requested. Completed Recycle Bin operations will not be rolled back.` and waits for shared Clean's final Result, preserving completed, skipped, failed, and history outcomes.
- The result page ends the current Clean session and renders path-free category outcomes for final empty, cleaned, partial, skipped, failed, and canceled states plus actual affected bytes, all projected from the authoritative final Result. Item-level Result and history keep `context_canceled` and every normal executed or skipped item outcome as the source of truth. Enter, Escape, or `b` returns to the main menu; `q` quits. The stale pre-execution preview and selection are never restored, and entering Clean again starts a new eager preview scan.
- TUI execution history records path-free structured provenance: `surface=tui`, `selection_mode=exact`, and canonical `selected_categories` in stable display-and-scan order rather than toggle order. It does not synthesize `clean --execute --opt-in ...` arguments or imply that an omitted default was authorized; CLI history keeps its current `args`, while normal item-level execution outcomes remain unchanged. These optional fields are an intentional backward-compatible additive change to `history --json`, not a change to Clean preview or execution JSON.

## References

- ADR 0012: eager measurement of every cleanup category in the Clean TUI only.
- ADR 0013: default selection is removable and TUI confirmation is exact.
- ADR 0014: active execution owns Ctrl+C until the final shared Result.
- ADR 0015: Protection exclusions may retain path-free category evidence.
- ADR 0016: exact TUI selection is recorded as structured history provenance.

## Preserved boundaries

- Preview scanning, browsing, and selection write no history or detailed candidate list.
- The TUI does not own candidate resolution, running-application gates, deletion, path safety, Protection rules, or Recycle Bin capacity decisions.
- CLI dry-run and Execute keep selected-only opt-in resolution. The eager unselected measurement exception belongs only to the Clean TUI preview.
- Clean preview and execution JSON contracts remain unchanged; `history --json` adds only optional path-free TUI provenance for TUI execution sessions.
- Confirmed execution remains Recycle Bin-only, validates fresh paths, and may produce different candidates or bytes than the preview.
