# Clean opt-in execution: opted-in opportunities and developer-tool caches become Recycle Bin executable

> **Status note (ADR 0018):** Opt-in remains the per-run valve and frozen-default contract described here. Catalog-owned `delete_permanently` for proven regenerable categories, per-run `--allow-permanent` / TUI permanent authorization, mixed-action execution, and the complete rule matrix in `docs/plan/clean-deletion-policy.md` supersede the "Recycle Bin only / no permanent-deletion path" language below. Recycle Bin capacity pre-checks still apply only to Recycle Bin work; permanent deletion is never a Recycle Bin overflow fallback. Foal still never runs third-party cleanup commands and never auto-elevates.

`foal clean --opt-in <name>` (repeatable) and `foal clean --opt-in all` let the user explicitly opt in, for the current run only, to clean specific skipped-by-default opportunity categories and developer-tool caches through the Windows Recycle Bin. Opt-in candidates are a new cleanup-item kind distinct from default candidates: the default candidate set stays frozen, opt-in never becomes default, and opt-in candidate bytes are reported as a separate `Opt-in reclaimable bytes` total, parallel to `Potential space` and `Observed opportunity bytes`, never merged into either. Opt-in affects both `--dry-run` (preview what would be cleaned) and `--execute` (perform the Recycle Bin deletion); `--execute --opt-in X` is additive, so default candidates are still cleaned and the opted-in categories are cleaned on top.

The safety model is preserved end to end. Deletion is Recycle Bin only; there is no permanent-deletion path and no automatic elevation. Protection rules still suppress protected paths before totals and execution. At `--execute`, opted-in categories are fresh-scanned and every delete path is validated immediately before deletion, so the executed set may differ from the dry-run preview (a temp entry may have been touched, a browser may have started, a cache may have been emptied). Running-application gating is tiered: browsers reuse the existing three-state detection and skip when running; tools with distinctive processes (go, cargo, dotnet, nuget, uv/`uvx`, bun/`bunx`) are detected and skip when running or unknown (fail closed, including missing state and snapshot failure; distinctive-process tools require idle before and after measurement); tools hosted under a shared runtime (npm/pnpm/yarn under node, pip under python) cannot be reliably attributed to the tool, so Foal proceeds with Recycle Bin recoverability and the existing safety note, because the user has explicitly opted in. Recycle Bin capacity is pre-checked: a volume whose Bin is disabled (`NukeOnDelete`) skips with `recycle_bin_disabled`, and an item larger than the volume's Bin `MaxCapacity` skips with `recycle_bin_capacity`, so `SHFileOperation`'s silent permanent-deletion overflow is never relied on.

Developer-tool caches (npm, pnpm store, yarn cache, go, pip, cargo, NuGet HTTP v3 cache, NuGet global packages, corepack, uv, Bun, structured Playwright browsers, structured Puppeteer browsers, and Electron download cache) are opt-in executable by Foal's own Recycle Bin action; Foal never runs the tool's own cleanup command, so ADR 0004's "never runs a tool's cleanup command" and "probes never run during `foal clean --execute`" still hold. Because probes cannot run at execute, opt-in dev cache paths are resolved with environment-variable and default-path rules (the Corepack-style resolution ADR 0004 already permits), consistently at dry-run and execute; a developer-cache category may resolve zero, one, or multiple roots, each normalized, deduplicated, protection-checked, running-application-gated, and measured per root. ADR 0011 extends this seam with optional structured child candidate discovery for mixed-state roots; categories without that private policy keep whole-root candidates. NuGet global packages (resolved from `NUGET_PACKAGES` or the current user's standard `.nuget/packages`) are a separate opt-in category from the NuGet HTTP v3 cache, so selecting the lightweight HTTP cache does not authorize the larger global-packages store. uv cache (identifier `uv-cache`) resolves from a non-empty `UV_CACHE_DIR`, otherwise the Windows standard user cache directory under `uv\cache`; Execute does not read `pyproject.toml`/`uv.toml`, does not infer invocation-specific `--cache-dir`, and never runs `uv cache dir`, `uv cache clean`, `uv cache prune`, or any other uv command. uv and `uvx` are one logical application for distinctive-process idle gating: either process running, unknown state, missing state, or snapshot failure fails closed before and after measurement. Bun cache (identifier `bun-cache`) resolves from a non-empty `BUN_INSTALL_CACHE_DIR`, otherwise the current user's official default `.bun\install\cache`; Execute does not read `bunfig.toml`/`.npmrc`, does not infer invocation-specific `--cache-dir`, and never runs `bun pm cache`, `bun pm cache rm`, or any other Bun command. bun and `bunx` are one logical application for distinctive-process idle gating with the same fail-closed idle-before-and-after rule. Config-customized paths (for example `.npmrc`, NuGet.Config, project-local uv cache-dir settings, or Bun config only visible via `bun pm cache`) that only a probe can see may be missed on Execute. This is deliberate: better to miss reclaimable space than to delete the wrong path or to run third-party binaries during execution. Dry-run Review still prefers a successful Bun query for display, with official env/default fallback when that CWD-sensitive query is unusable (ADR 0004).

**uv trade-off:** uv's documentation advises not to modify its cache directory directly and to use uv's own cache-modifying commands under its lock protocol. Foal still offers Foal-owned reclaim of the whole resolved uv cache root as an explicit per-run opt-in (catalog planned action `delete_permanently` per ADR 0018) because that stays inside Foal's safety model (no automatic elevation, no third-party command execution on Execute). The user must opt in for the run (`--opt-in uv-cache`, `--opt-in dev-caches`, `--opt-in all`, or Clean TUI selection) and authorize permanent deletion; uv/uvx must be idle with unknown fail-closed; paths are fresh-resolved and validated immediately before each permanent deletion; and preview surfaces a non-zero-impact notice that dependencies and disposable tool environments may need re-download or rebuild. Default dry-run without opt-in continues to show only the allowlisted `uv cache prune` Review suggestion.

**Bun opt-in:** Bun documents both its own `bun pm cache rm` and direct cache-directory removal as supported clearing methods. Foal still never runs Bun commands on Execute; it reclaims only the env/default-resolved root via catalog permanent deletion after explicit per-run opt-in (`--opt-in bun-cache`, `--opt-in dev-caches`, `--opt-in all`, or Clean TUI selection) and permanent authorization. bun/bunx must be idle with unknown fail-closed; paths are fresh-resolved and validated immediately before each permanent deletion; preview notes that future downloads may be required and that hardlinked project content can affect reclaimed space. A successful Dry-run probe path that does not exactly match the executable env/default Opt-in root remains Review-only; selecting `bun-cache` suppresses only a path-backed Bun suggestion with the same shared Windows path identity.

**pnpm store opt-in (`pnpm-cache`):** Resolves from non-empty `pnpm_config_store_dir` (pnpm v11+) or `npm_config_store_dir`, otherwise `$PNPM_HOME/store`, otherwise `$XDG_DATA_HOME/pnpm/store`, otherwise `%LOCALAPPDATA%\pnpm\store`. Shared-runtime policy (Node hosts pnpm; not attributable). Whole store root only; never project `node_modules` or virtual stores. Execute never runs `pnpm store path` / `pnpm store prune` or reads project config. Preview notes re-download and hardlink/offline impact. Included via `--opt-in pnpm-cache`, `--opt-in dev-caches`, `--opt-in all`, or Clean TUI selection with permanent authorization.

**yarn cache opt-in (`yarn-cache`):** Resolves from non-empty `YARN_CACHE_FOLDER`, otherwise the classic Windows global root `%LOCALAPPDATA%\Yarn\Cache`. Shared-runtime policy (Node hosts yarn). Project-local Yarn Berry `.yarn/cache` is never a default root. Execute never runs `yarn cache dir` / `yarn cache clean` or reads `.yarnrc`. Preview notes re-download and offline/private-registry impact. Included via `--opt-in yarn-cache`, `--opt-in dev-caches`, `--opt-in all`, or Clean TUI selection with permanent authorization.

We chose this because the driving goal is to let a user clean as much as possible within Foal's safety model, not by abandoning it. opt-in is the sanctioned valve: the plan already states that higher-risk rule groups require explicit opt-in, and every opportunity already carries `requires_explicit_opt_in`. Keeping Recycle Bin-only execution, no auto-elevation, frozen defaults, and fresh-scan validation is what makes Foal worth using instead of another aggressive cleaner; opt-in lets the user explicitly accept more risk for a run without making that risk default.

## Considered options

- **Relax the safety model for maximum cleanup (permanent deletion, aggressive defaults, automatic elevation)** - rejected: abandons Foal's product identity; the safety model is the product. opt-in achieves "as much as possible" without reversing Recycle Bin-only execution or frozen defaults.
- **opt-in only the eight existing opportunity categories, exclude developer-tool caches** - rejected: developer-tool caches are the largest reclaimable chunk on a developer machine, so excluding them makes "as much as possible" hollow. Including them via Foal-owned Recycle Bin deletion (not tool commands) stays within ADR 0004.
- **Relax ADR 0004 to run read-only probes at execute for accurate dev cache paths** - rejected: reverses "no third-party binary execution during execute." Environment/default resolution plus path-safety validation is safer and accepts missed customized paths, consistent with "rather miss than wrong-delete."
- **Trust dry-run probe-resolved paths at execute without re-resolution** - rejected: violates the fresh-scan invariant; a config file such as `.npmrc` could change between dry-run and execute.
- **Let `SHFileOperation` silently permanent-delete Recycle Bin overflow** - rejected: smuggles permanent deletion past "Recycle Bin only." Capacity pre-check plus skip honors the stance and reports the skipped items as boundaries.


JetBrains IDE caches (`jetbrains-ide-caches`) are now an implemented product-scoped structured Developer tools opt-in category (ADR 0017): standard `%LOCALAPPDATA%\JetBrains` parent only; anchored 2020.1+ standard-layout IntelliJ-platform product-version roots (IntelliJ IDEA Ultimate/Community, PyCharm Professional/Community, WebStorm, PhpStorm, RubyMine, CLion, DataGrip, DataSpell, GoLand, RustRover, Aqua, MPS, Writerside, Rider); exact `caches`/`index` children (Rider also `resharper-host`); independent distinctive-process product gates; Local History and non-allowlisted children permanently excluded; no JetBrains config/install/Toolbox probing or process stopping.

Visual Studio regenerable caches (`visual-studio-caches`) are an implemented structured Developer tools opt-in category (ADR 0020): standard `%LOCALAPPDATA%\Microsoft\VisualStudio` parent only; exact shared `Roslyn` and per-instance `ComponentModelCache` under anchored 14.0+ instance hives; devenv idle-before-and-after gate independent of VS Code/Cursor; Settings/Extensions/ProgramData/solutions permanently excluded; no install/registry/vswhere probing or process stopping.
## Consequences

This qualifies several prior postures. The review-only opportunity scan is no longer universally omitted from execution: opted-in categories are re-scanned at execute because their results are now executable opt-in candidates, while non-opted-in categories stay omitted. Developer-tool caches are no longer "Review suggestions only": they are Review suggestions by default and opt-in executable via Foal-owned Recycle Bin, never via the tool's command. Clean execution history no longer universally excludes opportunities: opted-in executed paths are recorded as item records with paths and opt-in sub-totals (`OptInDeletedCount`, `OptInAffectedBytes`), while non-opted-in opportunities stay excluded. The existing test invariant "opportunities never reach execute history" narrows to "non-opted-in opportunities never reach execute history."

New JSON contract surface appears: an `opt_in_candidates` array, an `opt_in_reclaimable_bytes` total, opt-in execution item results, and new skip reasons (`recycle_bin_disabled`, `recycle_bin_capacity`, per-tool running-application skips). `CONTEXT.md` gains the `Opt-in candidate` and `Opt-in reclaimable bytes` terms, and `Review suggestions`, `Review-only opportunity scan`, and `Opportunity history summary` gain opt-in caveats.

Default behavior is unchanged: `foal clean --execute` without `--opt-in` still cleans only the Foal-owned temp sandbox, and `foal clean --dry-run` without `--opt-in` still reports opportunities as non-executable review data. opt-in is purely additive and never becomes default. The TUI is out of scope for this decision: it stays read-only, and opt-in is a CLI flag concept; a future TUI opt-in preview would be a separate decision.

ADR 0009 supersedes only the TUI-specific read-only consequence above and the deferral of aggregate multi-item Recycle Bin capacity protection. All other decisions in this ADR remain in force.

NuGet global packages is now an implemented opt-in category (resolved from `NUGET_PACKAGES` or the current user's standard `.nuget/packages`), distinct from the NuGet HTTP v3 cache. uv cache is now an implemented opt-in category (resolved from `UV_CACHE_DIR` or the Windows standard user cache under `uv\cache`) with distinctive-process idle gating for `uv.exe`/`uvx.exe` and an explicit trade-off against uv's "do not modify the cache directory directly" guidance. Bun cache is now an implemented opt-in category (resolved from `BUN_INSTALL_CACHE_DIR` or the official user default `.bun\install\cache`) with distinctive-process idle gating for `bun.exe`/`bunx.exe`, CWD-independent Dry-run Review fallback, and no Bun command execution on Execute. Playwright browser binaries (`playwright-browsers`) are now an implemented structured Developer tools opt-in category: env/default root via non-blank `PLAYWRIGHT_BROWSERS_PATH` (trimmed `0` = no global root) or `%LOCALAPPDATA%\ms-playwright`, one-level child discovery of complete allowlisted component revisions, shared-runtime policy, MCP/profile/metadata exclusion, and catalog-owned permanent deletion (ADR 0018). Puppeteer browsers (`puppeteer-browsers`) is an implemented structured developer-cache opt-in category (resolved from non-blank `PUPPETEER_CACHE_DIR` or the current user home `.cache\puppeteer` root) that exposes independent Windows platform-version installations under allowlisted products via shared-runtime policy, never treating the root or product parents as candidates and never running Puppeteer/npx commands. Electron download cache (`electron-cache`) is an implemented whole-root Developer tools opt-in category (resolved from non-blank `electron_config_cache` or `%LOCALAPPDATA%\electron\Cache`) with shared-runtime policy, no Review suggestion probe, no Electron/npm/npx command execution, and a re-download/offline impact notice. Package/build caches, Application caches, Windows regenerating caches, and JetBrains IDE caches that are permanent-delete eligible are listed in ADR 0018 and `docs/plan/clean-deletion-policy.md`. Still deferred and requiring their own decisions: persistent opt-in configuration, further opt-in categories beyond the locked matrix, and any expansion of the default candidate set.

ADR 0012 further qualifies selected-only preview resolution for the category-first Clean TUI: that read-only surface may eagerly measure unselected opt-in categories, while CLI dry-run and every Execute path stay selected-only. After ADR 0009 enabled confirmed TUI execution, ADR 0013 creates a TUI-only exception to this ADR's additive CLI contract: defaults start selected but may be removed, and confirmed TUI execution represents the exact category selection. CLI opt-in remains additive.
