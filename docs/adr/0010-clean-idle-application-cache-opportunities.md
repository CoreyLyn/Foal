# Idle Application cache opportunities use fixed allowlists and application-idle gating

> **Status note (ADR 0018 + VS Code-family expansion):** Application cache categories use catalog planned action `delete_permanently` (with idle-before-and-after gates and re-fetch impact notices unchanged). Execute validates immediately before permanent removal; Recycle Bin capacity pre-checks do not apply to these permanent categories. Discovery, allowlists, and independent editor gates in this ADR remain in force.
>
> Registered complete Application cache categories are now: `vscode_cache` (`%APPDATA%\Code` / `Code.exe`), `cursor_cache` (`%APPDATA%\Cursor` / `Cursor.exe`), `vscode_insiders_cache` (`%APPDATA%\Code - Insiders` / `Code - Insiders.exe`), `vscodium_cache` (`%APPDATA%\VSCodium` / `VSCodium.exe`), and `windsurf_cache` (`%APPDATA%\Windsurf` / `Windsurf.exe`). All share the same fixed relative-root allowlist. Selecting or running one never authorizes or suppresses another.

Foal already reports browser-owned regenerating caches as skipped-by-default Opportunity categories after browser idle-before-and-after inspection (ADR 0007) and reclaims opted-in categories through shared Clean (ADR 0008, qualified by ADR 0018). Non-browser application-owned cache roots such as Visual Studio Code and Cursor need the same Opportunity model without reusing browser-named policy, browser `Local State` profile catalogs, or developer-tool Review suggestion probes.

This decision introduces **idle Application cache opportunities**: path-free Opportunity categories under the Developer tools report grouping, gated by a generic `application-idle-before-and-after-inspection` running-application policy. Discovery is confined to one reusable internal seam that accepts a registered application policy and an exact relative-root allowlist under the current user's standard Roaming AppData base. Each existing allowlisted directory becomes an independent Opportunity or Opt-in candidate with its own path and bytes. Foal never scans the user-data tree for cache-like names, never inspects process command lines, never discovers installations or portable/`--user-data-dir` roots, never stops the application, and never auto-elevates.

Registered complete categories are `vscode_cache` (label `VS Code cache`) for logical application `visual_studio_code` (`Code.exe`, case-insensitive) under `%APPDATA%\Code`, and `cursor_cache` (label `Cursor cache`) for logical application `cursor` (`Cursor.exe`, case-insensitive) under `%APPDATA%\Cursor`. Both share the same fixed allowlist: exactly `Cache`, `CachedData`, `CachedExtensionVSIXs`, `Code Cache`, `GPUCache`, `DawnGraphiteCache`, and `DawnWebGPUCache`. Each editor remains a separate category, root resolver, and Running application identity so selecting or running one never authorizes or suppresses the other. User settings, profiles, workspace/global storage, backups, installed extensions, Service Worker and web storage, Network/cookies/credentials, logs, Crashpad, and every unknown directory are excluded by construction. Missing or blank AppData or a missing editor root is silent absence. Pre-inspection running/unknown/missing state skips all roots for that application without measuring; post-inspection unsafe state discards every measured root and byte total for that application only. Incomplete or canceled inspection of one root contributes no bytes for that root; completed siblings may remain independently when the scan was not canceled. Protection suppresses protected roots before totals, projection, and history without authorizing siblings.

Cursor inclusion is deliberately conservative: Cursor lacks equally authoritative public source for every directory name. Do not broaden scope from VS Code ancestry or directory naming—only the exact PRD allowlist observed under the standard Cursor root is eligible.

Default Dry-run and the Clean TUI may observe idle roots only as skipped-by-default Opportunities and Observed opportunity bytes (never Potential space). Default Execute without Application cache opt-in performs no application process detection or cache inspection for these categories. Explicit `--opt-in vscode_cache`, `--opt-in cursor_cache`, `--opt-in dev-caches`, `--opt-in all`, or Clean TUI category selection converts resolved roots into Opt-in candidates for that run only; selecting one editor never selects the other. Execute fresh-resolves and re-inspects, validates immediately before each permanent deletion, and requires per-run permanent authorization (`--allow-permanent` or TUI confirmation). Non-opted-in history remains aggregate-only without editor paths; opted-in execution uses normal path-bearing history. Preview notes that `CachedExtensionVSIXs` holds downloaded extension packages that may need re-fetch while installed extensions and settings are not selected.

`dev-caches` expands from canonical catalog policy: registered developer-cache categories plus idle Application cache opportunities under Developer tools, not a second hardcoded list. Future editors must register their own category, application identity, and exact allowlist behind the same seam; they must not copy VS Code or Cursor logic or broaden into recursive user-data scanning.

## Considered options

- **Reuse browser-idle policy and browser discovery for editors** - rejected: browser `Local State` multi-profile complete-or-discard semantics and browser-named policy do not fit multi-root independent editor caches.
- **Model editor caches as developer-tool Review suggestions** - rejected: editors do not expose a Foal-suitable native cache-clean command contract for this slice; regenerating roots are Opportunity data when idle.
- **Treat entire `%APPDATA%\Code` or `%APPDATA%\Cursor` as disposable** - rejected: settings, state, credentials, and extensions must never enter the candidate set.
- **Infer custom roots via installation discovery or process command lines** - rejected: expands beyond the conservative standard Roaming AppData boundary and fails closed product posture.
- **Share one editor gate between VS Code and Cursor** - rejected: independent process identities are required so one running editor cannot suppress or authorize the other.

## Consequences

JSON, human, and Clean TUI surfaces keep existing Opportunity/Opt-in contracts; no editor-specific result schema is added. Domain glossary, AGENTS product boundaries, README/help examples, and category enumerations must list `vscode_cache`, `cursor_cache`, and the application-idle policy. Tests use shared Clean Dry-run/Execute as the primary seam plus injected Application cache discovery for deterministic app-data/process/filesystem cases, including independent editor gates. Default candidate freeze, catalog-owned planned actions (ADR 0018), no automatic elevation, and default Execute without opt-in remain unchanged.
