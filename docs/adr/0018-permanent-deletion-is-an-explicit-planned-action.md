# Permanent deletion is an explicit planned action, never a fallback

Foal may introduce permanent deletion for cleanup items whose eligibility is separately established, because moving large disposable caches to the Recycle Bin does not immediately release space on the same volume. Permanent deletion must be assigned and visibly disclosed as the item's planned action before execution confirmation; execution may complete, skip, or fail that action but must never substitute permanent deletion when the Recycle Bin is disabled, lacks capacity, rejects a target, or fails an operation. Deletion action is shared Clean category semantics rather than a presentation-surface exception: selecting the same category for execution through CLI or TUI must produce the same planned action, while the shared Clean core retains candidate resolution, validation, and deletion ownership.

Permanent-delete eligibility belongs to canonical cleanup rules. The Clean TUI automatically derives each selected category's action from those rules and offers no per-candidate deletion-method toggle. Its confirmation explicitly authorizes the disclosed permanent-delete portion of the exact selection. CLI derives the same planned actions but requires a dedicated per-run permanent-deletion option in addition to ordinary `--execute`; without equivalent authorization, shared Clean skips permanent-delete candidates and never reroutes them to the Recycle Bin. This qualifies ADR 0008 and ADR 0009 enough to permit the explicitly planned permanent-delete path classified and presented below.

A rule may qualify only when it precisely proves that every surviving candidate is regenerable or re-downloadable and contains no user-authored, diagnostic, configuration, history, or login state. Complete inspection, known layout, normal non-reparse paths, fresh resolution, Protection, and immediate validation remain mandatory; age, a cache-like name, or location under Temp is insufficient. Ambiguous Temp content and user or diagnostic state stay Recycle Bin actions. Rebuild, network, or offline cost does not remove eligibility, but such higher-impact categories remain Opt-in and must disclose that impact before confirmation.

Every executable canonical cleanup rule must explicitly declare one stable action: `move_to_recycle_bin` or `delete_permanently`. Choosing `delete_permanently` is the rule's eligibility declaration; there is no parallel eligibility boolean. Both actions require rationale and contract tests. Registration has no inferred default action, so adding a cleanup rule necessarily requires an explicit eligibility decision. Accepted permanent-delete rules currently include `user_temp`, `crash_dumps`, `explorer_thumbnail_cache`, `inet_cache`, `playwright-browsers`, `puppeteer-browsers`, `electron-cache`, `browser_cache`, `vscode_cache`, `cursor_cache`, `vscode_insiders_cache`, `vscodium_cache`, `windsurf_cache`, `trae_cache`, `d3d_shader_cache`, `nvidia_dx_cache`, `amd_gpu_shader_caches`, `intel_gpu_shader_cache`, `npm-cache`, `pnpm-cache`, `yarn-cache`, `go-cache`, `go-modcache`, `pip-cache`, `cargo-cache`, `nuget-cache`, `nuget-global-packages`, `corepack-cache`, `uv-cache`, `bun-cache`, `jetbrains-ide-caches`, `visual-studio-caches`, `grok-build-update-residue`, and `obsidian_cache`. Their existing Opt-in, fresh-resolution, structural exclusions, running-application policies, shared-runtime caveats, and impact notices remain mandatory; in particular, `CachedExtensionVSIXs` stays eligible as a downloaded package cache while retaining its re-fetch warning, uv/uvx keep fail-closed idle gating and the upstream direct-cache-modification warning, JetBrains Local History remains permanently excluded, and NuGet global packages warn that offline, private-source, removed, or inaccessible packages may not restore. `explorer_thumbnail_cache` and `inet_cache` now qualify for permanent deletion because exact research allowlists (thumbcache_*.db / iconcache_*.db under Explorer, and IE / Low\IE INetCache roots) restrict candidates to proven regenerable content; their whole-root predecessors were the only prior blocker.

`user_temp` and `crash_dumps` are permanent-delete rules, following the industry convention that disposable temp files and crash dumps are directly removed rather than moved to the Recycle Bin (moving them would not release space and would often exceed Recycle Bin capacity). The earlier regenerability concern is mitigated by the three control gates that remain mandatory: explicit Opt-in selection, per-run permanent-deletion authorization (`--allow-permanent` / TUI confirmation), and visible pre-execution disclosure that the action is irreversible. `windows_error_reporting` retains Recycle Bin policy because Windows Error Reporting data is non-recreatable diagnostic evidence the user may want to recover. Explicit Opt-in authorizes cleanup of any of these categories but does not remove the authorization or disclosure gates.

The default `foal_owned_temp_sandboxes` rule also retains Recycle Bin policy. Its current `foal-` / `Foal-` top-level Temp name match expresses intent but is not strong ownership or inactivity evidence. Default eligibility never implies permanent-delete eligibility; a future ownership marker, strict directory structure, and non-active lifecycle proof would require a separate decision before this rule could change action.

The Clean TUI uses one strengthened confirmation view rather than a second permanent-delete prompt. It splits the exact selection into Permanent deletion and Recycle Bin summaries with category count, candidate count, and measured bytes; labels every selected category with its planned action; states that permanent deletion cannot be recovered; and retains category-specific impact notices. One confirmation authorizes both disclosed groups. Execute still fresh-resolves candidates, so counts and bytes may change, but it may not introduce a deletion action type that the confirmation did not disclose.

Mixed-action execution performs fresh resolution, Protection, running-state gates, immediate path validation preparation, and applicable Recycle Bin capacity preflight for the full selected plan before mutation. A global safety or configuration failure performs no deletion. After preflight, shared Clean executes Recycle Bin actions first and Permanent deletion last. A category, candidate, or volume-local failure skips or fails only the affected work while safe siblings continue; completed actions are never rolled back, and final Result and History preserve partial outcomes by actual action.

The Clean TUI starts with the conservative default category plus every category whose rule has proven Permanent-delete eligibility selected, maximizing initial reclaimable coverage while leaving non-regenerable or currently over-broad Recycle Bin opt-ins unselected. The current catalog starts with 37 selected categories (1 default + 36 permanent); `windows_error_reporting` remains an unselected Recycle Bin opt-in (non-recreatable diagnostic evidence). Users may clear any initial selection, and confirmation authorizes only the visible exact set. This supersedes ADR 0013 only where it says every opt-in category starts unselected; CLI additive `--opt-in` behavior remains unchanged.

Result and History record the actual action for each successful item and split measured outcomes into `permanently_deleted_bytes` and `recycle_bin_moved_bytes`. Existing aggregate `affected_bytes` is their sum and means total successfully processed content, not released disk space. TUI and human output must not describe Recycle Bin moves or aggregate affected bytes as reclaimed space, and even permanently deleted bytes remain measured logical size rather than a promise of equal physical free-space gain.

CLI uses `--allow-permanent` as the dedicated per-run authorization. Dry-run never requires it and always reports each rule's true planned action. Execute without the option skips every selected Permanent deletion candidate with stable reason `permanent_deletion_not_authorized`, continues authorized Recycle Bin work, and never changes those candidates to Recycle Bin actions. The Clean TUI strengthened confirmation supplies equivalent authorization directly to shared Clean and does not synthesize CLI arguments.

Permanent deletion revalidates each candidate immediately before mutation. Recursive removal is continue-on-error: a file that cannot be removed (locked by another process, permission denied, reparse) is skipped and traversal continues, deleting the rest of the candidate tree. Deleted bytes are established reliably as the sum of file sizes actually removed during traversal, so a partially-removed candidate contributes its actually-deleted bytes to `permanently_deleted_bytes` and is recorded as a `permanent_delete_partial` failed portion for the remainder; the category projects to `partial` and the partial-risk warning still applies because some content was already permanently deleted. A candidate from which zero bytes were confirmed removed is `failed`, not `skipped`, with stable reason `permanent_delete_failed` and the partial-risk warning. History retains each item's planned and attempted action, original measured bytes, and outcome. Shared Clean neither rolls back nor sends remaining content to the Recycle Bin, and safe sibling candidates continue. The legacy fail-fast removal path remains available for removers that do not implement the detailed continue-on-error interface (used by purge and test fakes).

Permanent deletion means ordinary filesystem removal that bypasses the Recycle Bin. Foal does not overwrite file contents, perform multiple passes, shred files, wipe free space, or claim forensic non-recoverability; SSD behavior, TRIM, links, backups, and synced copies remain outside the cleanup model. Secure erasure is not part of Clean.

Permanent recursive removal checks cooperative cancellation during traversal so Ctrl+C does not wait for an entire large cache tree. Cancellation stops traversal and prevents further candidates from starting. An untouched candidate is `canceled`; a candidate whose mutation may have begun is also `canceled` but warns that some content may already be permanently deleted and contributes zero `permanently_deleted_bytes`. Completed actions are not rolled back, and the Clean TUI remains attached until shared Clean returns the authoritative final Result. This extends ADR 0014 from Recycle Bin operations to both deletion actions.

Deletion actions use stable contract values `move_to_recycle_bin` and `delete_permanently`. Every executable canonical category summary and Dry-run candidate exposes its `planned_action`; execution and History items expose the actual `action` while retaining planned action where relevant. The TUI consumes the shared read model rather than owning an action map. A parallel `can_permanent_delete` boolean is deliberately omitted because it could disagree with the action; catalog validation rejects missing or unknown action declarations.
